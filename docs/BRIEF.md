# Portal Hub: engineering brief (working copy)

Owner: K Line Europe GmbH (CEO Dr. Sherif Kandil). Decisions marked **fixed** change only with the CEO's approval. Never weaken a security control. Keep patient data out of logs, emails, webhooks, URLs, file names on disk and error messages. Interface text: plain friendly British English, short sentences, no dash characters as separators, dates like `24 Sep 2026`, numbers with thousands separators.

This file is the working copy of the brief for phases 1 and 2 plus the direct manufacturing zip flow. Later phases (production/MES, claims, specs, organisations, integrations, operations) follow the original brief and are not yet built.

## 1. Product

Secure web platform for client companies (aligner brands, labs, clinics) to send clear aligner case files to K Line Europe GmbH for manufacturing. Handles EU patient health data, so security and GDPR are core. Partners drop folders/zips (one folder per case). The platform reads case, arch and aligner step from names, checks each file (3D model integrity, trim line closure, malware, active content), encrypts each file with its own key and stores it in Germany. Clean cases go on to a K Line factory (MES pulls through an API, later phase). Bulk **direct manufacturing** cases are also pushed to the K Line customer portal API v2.6 (see section 12).

Demo companies are fictional only: Acme Aligners, Contoso Smile, Fabrikam Dental Lab. No real partner name in code, UI or docs.

## 2. Fixed decisions

1. MES is the source of truth for production (later phase).
2. At least one identifier per case: case ID or patient name. Names optional, encrypted, masked on screen, never printed on bags by default. (Direct manufacturing cases: patient first and last name are mandatory, see section 12.)
3. Hosting in Germany (Hetzner). No third party requests from the browser (no analytics, CDN fonts, external scripts).
4. Two factor sign in for everyone (password plus TOTP).
5. Per file encryption with keys held outside the database, plus field encryption for names and sensitive text.
6. Tenant isolation twice: application code and PostgreSQL row level security under a restricted role.
7. Uploads stay locked until the partner is active and a Data Processing Agreement (art. 28 GDPR) is recorded.
8. Transfer gate: EEA partner cases only produced in the EEA, an adequacy country, or with SCCs recorded.
9. Client agnostic (see above).
10. Self registration open but gated by email confirmation and K Line review.
11. Warnings need explicit confirmation by the partner, stored with the case. Nothing silently corrected.
12. Production spec versioned and signed by both sides; each case records its spec version.

## 5. Runtime

* One image, three processes: API, worker, CLI. In dev the worker runs inside the API (`RUN_WORKER=true`).
* Job queue in PostgreSQL (`jobs`, `FOR UPDATE SKIP LOCKED`, retries with backoff). Kinds: `file.process`, `email.send`, `case.recompute`, `notify.kline`, `bulk.push`.
* Every DB access goes through `tx(ctx, fn)`: one transaction first running `SELECT set_config('kph.org_id',$1,true), set_config('kph.bypass',$2,true)`. K Line users bypass on; partners and partner API keys run with own org id; system jobs use `SYSTEM = { orgId: null, bypass: true }`. Parse `int8` and `numeric` as numbers and `date` as plain `YYYY-MM-DD` string.
* API serves the built web app with SPA fallback: unknown GET paths outside `/api/` return `index.html` with `cache-control: no-cache`; hashed assets cached a year; unknown `/api/` paths return `404 {code:'not_found'}`.
* Config via env validated by zod (server/.env loaded only in development): `NODE_ENV HOST PORT(4000) PUBLIC_URL TRUST_PROXY DATABASE_URL (role kph_app) DATABASE_OWNER_URL (kph_owner, migrations/CLI) MASTER_KEYS (JSON key id -> 32 byte base64) ACTIVE_KEY_ID BLIND_INDEX_KEY_ID HASH_KEY_ID(default BLIND_INDEX_KEY_ID; keys API key, recovery code and CSRF hashes, never rotates) STORAGE_DRIVER(fs|s3) STORAGE_DIR S3_* SCANNER(clamav|none) CLAMAV_HOST CLAMAV_PORT SMTP_URL MAIL_FROM SESSION_IDLE_MINUTES(30) SESSION_MAX_HOURS(12) STEP_UP_MINUTES(10) SCRYPT_LOG_N(17) SIGNUP_ENABLED SIGNUP_DAILY_LIMIT SUPPORT_EMAIL PRIVACY_EMAIL RUN_WORKER DEMO_MODE TUNNEL_HOOKS_ONLY(dev only) ALLOW_NO_SCANNER AUDIT_RETENTION_MONTHS(36) WEB_DIST OIDC_GOOGLE_CLIENT_ID OIDC_GOOGLE_CLIENT_SECRET OIDC_ALLOWED_DOMAIN OIDC_REQUIRE_LOCAL_MFA(only true: any other value stops the server from starting) OIDC_GOOGLE_DISCOVERY_URL`.
* Production refuses to start when `PUBLIC_URL` not https, `DEMO_MODE` or `TUNNEL_HOOKS_ONLY` on, no scanner (unless allowed), no SMTP, S3 driver lacks bucket/endpoint.

## 6. Security design

**DB roles and RLS.** Migrations run as `kph_owner`. App connects as `kph_app`: `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS`, owns no table, password at least 16 chars, created/updated by the migration runner from `DATABASE_URL`. Functions `kph_bypass()`, `kph_org()`, `kph_can_access(org_id)` read the session settings. Policy `tenant_isolation` (`USING kph_can_access(org_id) WITH CHECK kph_can_access(org_id)`) on every tenant table; on `organizations` by `id`. Policy `kline_only` (bypass required) on `oidc_flows`, `mes_stage_map`, `mes_events`, `dev_mailbox`. `users`, `user_tokens`, `sessions` carry `org_id` and are tenant isolated. App role gets SELECT/INSERT/UPDATE/DELETE except audit tables.

**Audit log.** Append only, hash chained. `kph_audit_append(...)` SECURITY DEFINER computes `hash = sha256(prev_hash || canonical entry)`; `kph_audit_verify()` walks the chain; `kph_audit_trim(before)` owner only. App role has SELECT only on `audit_log`, no access to `audit_anchor`. Every security relevant action audited: actor type (`user api_key service system`), actor, org, action, target, IP, user agent, details. Partners read their own org's entries including every K Line access to their files and every revealed patient name.

**Encryption.** Files: random 32 byte data key per file; 8 MB chunks each sealed AES-256-GCM; nonce = 8 byte random prefix + chunk index; AAD `chunk|<fileId>|<idx>|<count>`. Data key wrapped with KEK derived by HKDF from `MASTER_KEYS[ACTIVE_KEY_ID]`; key id stored with file. CLI `rewrap` re-wraps every file data key and re-encrypts every field token under the active key (`--dry-run`, `--only`, batches, idempotent, verification pass); API key hashes, recovery code hashes and CSRF tokens are keyed by `HASH_KEY_ID`, which does not rotate. Fields: `f1.<keyId>.<iv>.<ciphertext>.<tag>` (base64url, AES-256-GCM) with AAD binding row and column: `case|<id>|patient`, `case|<id>|notes`, `file|<id>`, `user|<id>|totp`, `webhook|<id>`. Blind index: HMAC of normalised patient name (case, accents, spacing removed).

**Sign in.** scrypt (N=2^17 prod), at least 12 chars, refuse common or containing email/name; constant time compares; dummy verify for unknown accounts. Lockout: 5 failures -> 15 min, doubling, max 24 h. Wrong second factor codes (authenticator, recovery and step up codes) are counted per user across all sessions: five within 15 min lock the account the same way (15 min, doubling, max 24 h) and end every session; a correct password never resets that counter, only a correct code, an administrator unlock (`POST /api/team/:id/unlock`, `/api/staff/:id/unlock`) or a password reset by email link does. TOTP RFC 6238 (SHA-1, 30 s, 6 digits, window one step each side), mandatory for all, replay protection (last used step), ten one time recovery codes stored as HMACs. Session stages `password`, `mfa_setup`, `full`. Server side sessions: 256 bit token in HttpOnly Secure SameSite=Strict cookie `__Host-kph_session` in production (`kph_session` in dev); only SHA-256 stored; idle 30 min, absolute 12 h; revoked on password change, role change, disabling, MFA reset. **CSRF:** every write with a session needs header `x-csrf-token` = HMAC of the session id. Exempt: `POST /api/auth/login`, `/api/auth/password/forgot`, `/api/auth/password/reset`, `/api/auth/invite/accept`, `/api/auth/register`, `/api/auth/verify`. **Step up:** sensitive actions need TOTP in the last 10 minutes else `403 step_up_required`. **Google Workspace sign in (K Line staff only):** `GET /api/auth/oidc/google/start` and `/callback` (authorisation code flow with PKCE S256; state and nonce stored hashed in `oidc_flows`, 10 minutes, single use, bound to the browser by a cookie; ID token checked for RS256 signature, issuer, audience, expiry, nonce, `email_verified` and `hd`); the staff account must already exist, nothing is created; Google is only the first factor, so the session is always created at stage `password` (or `mfa_setup`), never `full`, until the authenticator code is given (`OIDC_REQUIRE_LOCAL_MFA` can only be `true`: two factor sign in is required for everyone); every failure redirects to `/login?error=google`. `GET /api/public/config` carries `googleSignIn`. Demo mode also serves `GET /api/demo/sample-cases.zip` (four fictional sample cases). Invited user who set a password can sign in and go to authenticator setup.

**API keys.** `kph_<12 hex prefix>_<43 base64url secret>`, hash stored, shown once, scopes, optional CIDR allow list, expiry up to 730 days, rate limited per key.

**HTTP hardening.** Strict CSP (`default-src 'self'`, no inline script, `frame-ancestors 'none'`), `X-Frame-Options: DENY`, HSTS preload in prod, `Referrer-Policy: no-referrer`, nosniff, `cache-control: no-store` on `/api`. Rate limits: global 900/min per API key prefix or IP; auth endpoints 10/min; forgot password 5/min. **Logging:** never log cookies, authorization headers, CSRF tokens, request bodies; redact `token=` in URLs and path segment after `/api/auth/invite/` (except `accept`). Files served back only behind auth, with `Content-Disposition: attachment` or sandboxing CSP, nosniff, no public or presigned URLs.

## 8. Case lifecycle (phases 1 and 2)

Statuses: `draft submitted on_hold ready received in_production shipped delivered cancelled`. Draft: files can be added/removed; checks recomputed after every change. **Errors block submission:** STL or PTS without arch and step; two files for same aligner and kind (template files are a separate kind slot: a template U01_T does not clash with U01); a file rejected by checks; no STL at all. **Warnings need explicit confirmation:** missing PTS for an aligner (when `require_pts`), trim lines without matching model, missing steps between first and last, warnings from single files, trim line not on its model. **Submit:** requires no errors and, with warnings, `acknowledgeWarnings: true` (stored). With `manual_review` the case goes to `submitted` (and a case that was on hold always goes to `submitted` when the partner submits it again); otherwise `ready` at default site or first allowed site that may legally receive it (transfer gate, `403 transfer_blocked`). Due date = `sla_days` business days (default 3) after ready. Self registered partners start with `manual_review` on. Instructions (encrypted, max 8,000 chars) editable in `draft submitted on_hold ready`; after that `409 instructions_locked`. Case ID rules: letters, digits, spaces and `_ . / # -`, max 64 chars, no `..`, no dot or slash at the start or the end, unique per partner among new standard cases (a direct manufacturing patient ID may repeat).

**Erasure on request.** `POST /api/cases/:id/erase` (permission `case.erase`: partner `admin` for the own organisation, `kl_admin` for any case; step up; the case reference must be typed as `confirmRef`) removes the case's files (all stored chunks, file rows to `purged`, key material cleared, bytes still used by a live file of a replacement or rework case kept) and the patient data now, by the same code as the retention purge, and keeps only the non identifying production record. Drafts are refused (`409 use_delete_for_drafts`), an erased or purged case answers `409 already_erased`. It writes the case event `erased`, the audit entry `case.erased` and a notice to the organisation's administrators, none with patient data. For direct manufacturing cases the K Line portal keeps its own copy and the answer says so (`portalCopyRemains`). A purge or an erasure also scrubs (`services/scrub.ts`) the patient ID of direct cases, hold reasons, claim free text and the case ID in webhook payloads.

**Transfer gate re-checks.** Besides submit and routing, the gate (fixed decision 8) is checked when the factory pulls cases or downloads a file and once a day in the retention job. A `ready` or `received` standard case whose site is no longer legal goes `on_hold` with a fixed reason. Direct manufacturing cases are produced by the K Line portal, have no site and are not subject to the gate.

## 9. Intake

**Upload protocol:** `POST /api/uploads` (purpose, case, name, size, arch, step, template flag) creates file, returns received chunks; `PUT /api/uploads/:id/chunks/:idx` (`application/octet-stream`, at most 8 MB, header `x-chunk-sha256`, mismatch -> `checksum_mismatch`); `POST /api/uploads/:id/complete` verifies all chunks and queues processing. Resumable. Limits: case files 512 MB, logo 5 MB, documents 50 MB, at most 600 files per case. Case file types: `stl pts pdf csv svg txt xml json jpg jpeg png`; executables always refused. Uploads only for case in `draft` or `on_hold`.

**Processing (worker):** ClamAV scan (`infected` rejects), then content checks. STL: binary/ASCII, bounding box; larger than 150 mm or smaller than 20 mm warns about units; vertices welded at 1 micrometre, open and non manifold edges counted (warnings); more than 1% zero area triangles warns; edge analysis up to 3 million triangles. PTS: points parsed; more than 10% unreadable lines is an error; declared count mismatch warns; closed when gap between first and last point is at most max(0.3 mm, 3 x median segment); breaks longer than max(3 mm, 10 x median) warn; fewer than 30 points warns; trim line must sit inside its model's bounding box. PDF: `/JavaScript`, `/JS`, `/Launch` blocks; embedded files and password protection warn. SVG: scripts, event handlers, `javascript:` links, `foreignObject`, external refs block. CSV: non UTF-8 warns; cells starting with `= @ + -` followed by text warn (formula injection; plain numbers such as `-19.622` are fine). Images checked by magic bytes. Processing recomputes the case checks in the same transaction.

**Folder intake (browser)**: see `shared/filenames.ts`. Files grouped per top level item (dropped folder or zip). Below it, the first folder level where paths differ holds the case folders. Structural sub folders never become cases: Upper Lower Maxilla Mandible Oberkiefer Unterkiefer OK UK UJ LJ U L (optionally followed by jaw/arch/models/steps), Steps Stages Subsetups Setups Aligners Trays Models STL PTS CSV Trim lines Cut lines Templates Attachments Exports Files 3D Scans Prints Output Results Photos Images Pictures Documents Docs Reports Prescriptions Rx Instructions Notes PDFs Other Misc Extras (optionally followed by a number). Case ID = ID in the case folder name (token with 4+ digits that is not a year or date), else the folder name cleaned. Arch from folder/file names (upper, maxilla, oberkiefer, superior, U, UP, OK, SUP, MAX, MX, UJ, TOP and lower equivalents, also `U04`); step from Step/Stage/Subsetup/Setup/Aligner/Tray words, `U04`/`L06`, or trailing number; templates from names containing Template (step 0) **or a `_T` suffix such as `90002_U01_T.stl` (template for step 1)**. Review screen lists one row per case with editable file mapping. Zips up to 2 GB and 5,000 entries are opened in the browser; the server never unpacks archives. Instructions files (`.txt .md .rtf .docx`) are read in the browser and become case instructions (max 8,000 chars); `.doc` not read.

## 12. Direct manufacturing bulk intake by zip (section 26) and KLINE API 2.6

Partners can create **direct manufacturing** cases in bulk by uploading a zip (or dropping folders). The zip holds one folder per case. The folder name carries the mandatory data: `<patient id> <first name> <last name>`, for example `55813 Marc Alonso`. Confirmed with the owner: product type does NOT appear in the zip and is ignored (default product type 0, Clear Aligners, is used when pushing). Other document files (pdf, images, csv, stl, pts, and so on) inside the case folder are the case's other documents. Because name order is not reliable across partners (examples: `90001 Kowalski Jan (2)` looks like `<id> <last> <first>`; `90002 Greta Kask Lind` is ambiguous), the review screen shows the parsed first/last name, offers a "Swap names" control, and blocks the case until patient ID, first name and last name are all present and confirmed. Trailing `(2)` style copy suffixes are stripped from the folder name.

Sample zip (`docs/samples`, from a partner): two case folders, each with `STL/`, `PTS/`, `CSV/` sub folders holding files `<id>_U01.stl`, `<id>_L11.pts`, `<id>_L11_T.stl` (template), `<id>_U01.csv` (laser marking text, tab separated: LaserPt1Start, LaserPt1End, text1, LaserPt2Start, LaserPt2End, text2). STL files are about 20 MB each; a case has about 41 to 42 of each type.

**Push to the portal (worker job `bulk.push`)** once a direct manufacturing case is submitted and its checks pass: the Hub creates the case in the K Line customer portal via the API v2.6 (base `/api/v2/`, headers `X-Kline-Api-Key`, `X-Kline-Api-User-UUID`, optional `X-Kline-Doctor-Id`, JSON bodies):

1. `POST /cases` with `first_name`, `last_name` (required, max 50), `gender` (required by the API; the Hub uses 2 "Prefer not to say" unless the partner supplies it), `product_type` 0, `doctor_instructions` from instructions, other fields default.
2. `POST /cases/{uuid}/files/{field_name}` for each file, binary stream with `Content-Disposition: attachment; filename="..."` or multipart. Allowed fields: `field_case_upper_scan`, `field_case_lower_scan`, `field_case_bite_scan` (stl obj ply dcm, draft only), `field_case_radiographs`, `field_case_clinical_photo_01..09` (png jpg jpeg), `field_case_other_docs` (zip tar png jpg jpeg pdf stl rar 7z, any status). PTS and CSV are not accepted extensions, so per case the Hub bundles every file the portal does not accept (PTS, CSV, and stepped STL models) into one zip streamed with yazl and uploads it to `field_case_other_docs`.
3. `PATCH /cases/{uuid}/submit`.

Store `portal_case_uuid`, push status and last error on the case (never patient data in error text); retry with backoff; emit case events `portal_pushed` / `portal_push_failed`. Credentials (API key and user UUID, optional doctor id, base URL) per partner in `organizations.settings.portal_api`, key stored field encrypted. The client is behind an interface (`PortalClient`) so a fake can be used in tests and later API versions plugged in. Responses use `{message, data, ...}`; anything other than 200/301/302 carries an error message. Case statuses: New, InPlanning, PendingPlanReview, PlanRejected, InProduction, Shipped. The API will change later: keep the adapter thin and versioned (`portal/v2.ts`).

## 13. Tests

Unit: envelope encryption (tampered/swapped/truncated chunks fail), field encryption and blind index, TOTP against RFC 6238 vectors, passwords, file checks (STL, PTS, PDF, SVG, CSV), file name parsing (incl. `_T` templates), shared rules (permissions), folder grouping (single case folder, batch folders, zips, nested exports, loose files, accents), bulk folder name parsing, instruction reading. Integration against real PostgreSQL through the HTTP layer with the restricted role: serves web app and deep links, unknown API paths 404, same answer for wrong password on known/unknown accounts, TOTP required before data, CSRF refused, uploads blocked until DPA on file, upload/checks/submit with chunk checksum rejection and warning acknowledgement, tenants isolated at API and DB, every name reveal and file download logged and visible to partner, audit chain verifies and app role cannot update/delete it, request logs never contain one time tokens, instructions encrypted at rest and editable until factory starts, bulk zip cases created with mandatory names and pushed to a fake portal client.
