# Open decisions and known gaps

Last updated: 6 Oct 2026.

This list collects decisions that are still open and gaps that the engineers reported during phases 1 to 6. Each item has a suggested owner (a role, not a person) and a next step. Owners are suggestions: the CEO (Dr. Sherif Kandil) assigns them. Decisions marked **fixed** in `BRIEF.md` change only with the CEO's approval.

Note on sources: section 24 of the original brief (the list of open decisions) is not part of the working copy `docs/BRIEF.md`. Items A1 to A7 follow the list given for phase 7 and describe how the current software behaves. Check them against section 24 of the original brief.

## B. Gaps reported by the engineers in phases 1 to 6

| # | Gap | Effect | Owner | Suggested next step |
|---|---|---|---|---|
| B1 | **Free text claim fields are not encrypted.** Claim summary, description, item notes, claim messages, hold reasons, factory event notes and material names are plain text. | A person may type a patient name or health detail. Since 5 Oct 2026 claim text, hold reasons and event notes are replaced by `[removed]` when the case is purged or erased, but they stay plain text while the case lives. | Engineering, Legal and Compliance | Decide whether to encrypt these fields (AAD bound like the others), shorten their retention, or accept with the warnings in the interface. |
| B2 | **Webhook delivery is not tested over real TLS.** Tests use `http://localhost`, which is allowed only outside production. | Certificate handling, SNI and redirects to real hosts are untested. | Engineering | Test against a public test endpoint with a valid certificate and a self signed one (must fail) before go live. |
| B3 | **Direct manufacturing shipped counts come from upper plus lower.** The K Line portal reports no count of shipped aligners for direct cases. The Hub uses `aligners_upper + aligners_lower` when no count is stored. Templates are not counted. | Invoices built from the shipments feed can differ from reality if a partner ships fewer or more aligners than planned. | Finance, Production | Agree with the portal team whether it can report a count. Until then, tell partners how the number is derived (the partner guide and API docs already do). |
| B4 | **ClamAV stream limit.** clamd refuses streams above its `StreamMaxLength` (25 MB by default). Case files can be 512 MB. | Large honest files are rejected with `scan_failed` (it fails closed). | Engineering, Operations | `deploy/clamd.conf` now sets `StreamMaxLength` and `MaxFileSize` to 600 MB. Test a 512 MB file through the real scanner before go live and keep the setting when the image is updated. |
| B5 | **Registrant data stays on the organisation record.** The registrant's name, email, website and volume remain in `organizations.signup` after approval. | No defined retention for this personal data. | Legal and Compliance | Decide a retention period, or remove the fields when the company is approved. |
| B6 | **Portal status sync polls every 10 minutes.** The K Line portal API has no callback, so statuses can be up to 10 minutes late. There is a Refresh button and `cli portal-sync`. | Partners may see a delay for direct cases. | Product | Ask the portal team for a webhook. Otherwise shorten the interval (200 cases per run cap) or keep and tell partners. |
| B7 | **Instruction edits after a push are not sent to the portal.** Changing instructions on a direct case after the push stores the change and tells K Line intake, but the portal keeps the old text. | The factory behind the portal may work from outdated instructions. | Product, Production | Lock instructions for direct cases after the push, or add an update call if the portal supports it. |
| B8 | **Replacement orders are refused for direct cases** (`409 direct_case`). A rework after an accepted claim is created as a standard case so the factory system can make it. | Partners must use a new direct batch for a replacement. | Product | Decide whether to support replacements for direct cases, for example as a new direct case copied from the original. |
| B9 | **Standard "Send files" screen removed on the owner's decision on 5 Oct 2026.** Partners now send cases in the Hub only through Direct manufacturing (`/portal/send/bulk`, a zip or folder with one folder per case). The old address `/portal/send` redirects there. Standard cases can still be created through the partner API (`/api/v1`) and by K Line staff. The server routes (`POST /api/cases`, file upload, submit) remain, so standard cases, the case page for existing standard cases, "Add files" on drafts, claims and replacements keep working. | Partners without an API integration have no screen to create a standard case, and the case ID pattern in the company profile is no longer used by any partner screen. | Product | Confirm that partners who need standard (non portal) production use the API or ask K Line staff. Decide whether to remove the case ID pattern setting from the company profile. |

## F. Exploratory test of 6 Oct 2026: what was fixed, what was left, what needs a decision

An exploratory tester went through the development Hub that the owner publishes through cloudflared. Details of the controls are in `SECURITY.md` (sections 2, 3, 9, 10, 12 and 20).

### Fixed

| # | Finding | Fix |
|---|---|---|
| F1 | **High.** The wrong code counter was per session, so a new password sign in gave five fresh authenticator guesses. | Wrong authenticator, recovery and step up codes are counted **per person across sessions**: five in 15 minutes lock the account (15 minutes, doubling, at most 24 hours) and end every session. A correct password does not reset the counter; a correct code does. Migration 011 (additive: `mfa_failed_codes`, `mfa_fail_window_start`, `mfa_lockout_count`). |
| F2 | **High.** With `DEMO_MODE=true` the demo routes (password, live authenticator codes, mailbox, registration links) and the demo hints in `/api/auth/me` answered anybody on the public tunnel. | They answer only to direct local use: no `x-forwarded-for`, `forwarded`, `cf-connecting-ip`, `cf-ray` or `x-real-ip` header and a loopback or private socket peer, else `404`. New `TUNNEL_HOOKS_ONLY` (default off, refused in production): through a proxy only `/api/hooks/kline-portal/<id>` and `/api/health` answer. |
| F3 | Resubmitting a case from hold sent it straight back to `ready` (hold bypass). | Always `submitted` (manual K Line review) after a hold, from K Line or the factory. |
| F4 | Weak passwords accepted (`password1234567`, `Admin@123456789`, `qwertzuiopasdf`, `1qaz2wsx3edc4rfv` and more). | Normalisation, a list of about 1,000, any tail after a common stem, sequences and keyboard rows, repeats, single character class under 16. A password change must differ from the current password. |
| F5 | An API key without `patients:read` saw `patientMasked` and `hasPatientName` on the session style routes. | Removed from every JSON answer for such a key (one response hook), and such a key cannot search by patient name. |
| F6 | A password reset did not lift a lock. | A reset also clears `locked_until`, `lockout_count` and the code counters. New `POST /api/team/:id/unlock` (and `/api/staff/:id/unlock`): step up, audited, a Locked badge and Unlock button on the Team and Staff pages. |
| F7 | A NUL character in any text gave HTTP 500. | One early check refuses it (query, parameters, nested JSON body) with `400 invalid_request`. |
| F8 | `DEMO_SCRIPT` and the guide did not say that admins must switch the menu items on for the Quality role. | Updated. |
| F9 | The factory could ship or deliver with silly times, and `DELIVERED` skipped `SHIP`. | Times earlier than the case's creation minus 24 hours, or older than 3 years, are errors; `DELIVERED` before `SHIP` is ignored ("Send SHIP before DELIVERED."). |
| F10 | `TRUST_PROXY` was false behind the tunnel. | The setting accepts `loopback` and comma separated lists and rejects anything else at start. The owner sets `TRUST_PROXY=loopback` in `server/.env` (not edited by the engineers). |
| F11 | Materials, Team and ERP and API pages were wider than a phone screen. | The page grid now lets its children shrink, so tables scroll inside their own box. |
| F12 | Smaller items: stock cannot go below zero (`409 would_go_negative`); a manual webhook retry clears `delivered_at`; a long file name keeps its extension; duplicate aligner and defect items in a claim are refused; hidden text direction characters are refused in file names, spec clauses, team names, material names and claim text; case IDs cannot contain `..` or start or end with a dot or slash; the stage map refuses duplicate codes whatever their capitals and needs step up; the factory intake writes one audit entry per call. | Done, each with tests. |

A time dependent test (`phase6`, claims filtered by today's date) used the UTC date while the API uses Berlin time, so it failed every evening between 22:00 and 24:00 UTC. The test now uses the Berlin date.

### Deliberately left as it is

* Notification read state, the global uniqueness of MES event ids, and the order of the rate limit and the audit check on `GET /api/audit/verify`.
* `GET /api/auth/me` for people who are not signed in, and what the page shows before sign in.
* **Intake `download_url`** is built from `PUBLIC_URL`. The factory system follows that address to download files, so `PUBLIC_URL` must be a **stable public address** in production. A changing quick tunnel address would break the links in every cached intake answer.

### Decisions for the owner

1. **Set the tunnel settings in `server/.env`:** `TRUST_PROXY=loopback` and `TUNNEL_HOOKS_ONLY=true`. Until then the public tunnel still serves the whole Hub (with the demo helpers hidden from it), and every visitor shares one rate limit.
2. **Intake audit entry belongs to K Line only.** One entry per intake call (count and up to 20 references) is written to K Line's own log, so a partner's access log no longer shows each factory poll. It still shows every file the factory system downloads. If partners must see polls, write one aggregated entry per partner per call instead.
3. **Locking is also a way to annoy someone.** Anybody who knows a password can lock that person out for 15 minutes by entering five wrong codes (and the same was already true for five wrong passwords). This is the price of closing the brute force hole; an administrator can unlock from the Team page and a password reset lifts the lock. If this matters, add an email notice to the person when their account is locked.
4. **A held case now always waits for K Line.** Partners with `manual_review` off used to resubmit straight to production. Confirm that the extra step is wanted for them (it is the fix for the hold bypass).
5. **Password rules apply from the next password change or reset.** Existing passwords stay valid. The word list is local (about 1,000 entries); there is still no breach list check (`SECURITY.md` section 2).
6. **Keyboard rows of four characters are refused** (for example `qwer`, `asdf`), except that `erty` alone is allowed because it is inside ordinary words such as "property" and "liberty". A passphrase that happens to contain another four character run (for example `azer`) is asked to change.
7. **Demo hints stay reachable on the local network.** A person on the same private network who can reach the dev Hub directly (no proxy) still sees the demo accounts when `DEMO_MODE=true`. `HOST` is `127.0.0.1` by default, so only this computer reaches it unless someone changes `HOST`.
8. **Migration 011** must be applied to the development database (`npm run migrate`). It is additive. The engineers applied it at the end of their work.
