Conventions are those of PHASE2_CONTRACT: JSON under `/api`, session cookie plus `x-csrf-token` on writes, errors `{code, message, ...extra}`, camelCase for everything the web app sees. The factory API (`/api/mes/v1`) is snake_case because it is an external interface. Send `{}` as the body of POST requests without data. "Step up" means an authenticator code within the last 10 minutes, else `403 step_up_required`. Every route below under "K Line" answers `403` to partner users even when they hold the permission name (partner admins hold `audit.read`, `file.download` and so on), and to service keys.

Direct manufacturing cases (`manufacturing_mode = 'direct'`) are pushed to the K Line customer portal and are NOT pulled by the MES. The MES intake only lists `standard` cases, and stage events for a direct case are errors. Direct cases still appear in the console lists.

## Stages and status

Statuses: `draft submitted on_hold ready received in_production shipped delivered cancelled`. MES stages in order: `received` (Received at factory), `printing` (3D printing), `thermoforming`, `trimming`, `finishing` (Finishing and cleaning), `quality_check`, `packing`, `shipped`, `delivered`. Stages printing to packing map to status `in_production`; `received`, `shipped`, `delivered` map to the status of the same name.

`shared/stages.ts` holds: `STATUSES`, `STAGE_IDS`, `STAGES` (id and label), `stageIndex`, `stageLabel`, `statusForStage`, `stepperSteps({status, stage, portalStatus?})` (the four step bar, see the last section), `simpleStatus`, `portalStatusToHub`, `MAP_TARGETS`, `DEFAULT_STAGE_MAP`, `STAGE_CODE_RE`. Stepper rules: draft: Submitted current; submitted or on hold: Submitted done, Files checked current; ready: both done and every stage upcoming; from received on, stages before the current one are done and the current one is `current`; delivered: all done; cancelled: only Submitted done.

After a case is `ready`, its stage changes only through MES events, a CSV import of MES events, or a manual update by staff with `stage.manual`. All three use one engine (`services/stageEngine.ts`, pure decision function `planTransition`):

* Stages only move forward. A stage older than or equal to the current one is `ignored` with the message "The case is already at or past that stage." A case that is `ready` again after a hold has no current stage, so any stage is forward.
* `shipped` needs carrier (max 60), tracking number (max 100) and aligners shipped (1 to 5,000), from every source. It records them, sets `shipped_at` (the event time, never in the future), `finished_at` if empty and `purge_after = shipped_at + the partner's retention_months`. `delivered` sets `delivered_at` (and the same shipped fields if the case never shipped through the system). Any stage sets `received_at` if empty; printing to packing set `started_at` if empty; packing, shipped and delivered set `finished_at` if empty.
* HOLD (from submitted, ready, received, in_production): status `on_hold`, `hold_reason` visible to the partner (factory system without a reason: "The factory has put this case on hold. K Line will be in touch."; staff must give 3 to 500 characters). A second hold, or a hold on shipped, delivered or cancelled, is `ignored`.
* CANCEL (from submitted, on_hold, ready, received, in_production): status `cancelled`, `cancelled_at`, `purge_after = now + 30 days`. Shipped, delivered or already cancelled is `ignored`.
* A stage for a case that is draft, submitted or on hold is an `error` (`case_not_in_production`). For a cancelled case it is `ignored`. For a direct case it is an `error` (`direct_case`).
* Each applied change: updates the case, adds a case event (`stage` for manual updates with the staff member as actor, `stage_reported` for factory events and CSV rows, `on_hold`, `cancelled`), writes an audit entry to the partner organisation (`case.stage`, `case.on_hold`, `case.cancelled`; actor `service` for the factory API, the user for CSV and manual), adds a `notifications` row for every active user of the partner (kinds `case_stage case_shipped case_delivered case_on_hold case_cancelled`, title = stage label or a short phrase, body `Case <ref>`, no free text and no patient data), and calls `emitCaseWebhook(c, caseId, event)` from `services/webhooks.ts` (a no op until phase 6; events `case.stage_changed case.shipped case.delivered case.on_hold case.cancelled case.ready case.rerouted case.released`).
* When a partner submits again (from draft or on hold) the case gets stage, received, started and finished timestamps cleared; `mes_case_id` is kept.

Case events carry `data.sourceLabel`, and the event list in the case detail has a computed `sourceLabel`: `Partner`, `K Line`, `Factory system` (factory API, CSV rows) or `System`.

## MES API (service key, base `/api/mes/v1`, no session, scopes checked)

Only a K Line service key with the scope works; sessions and partner keys get `403`, no key or a bad one `401`. Service keys never work on `/api/*` partner routes (they hold no case permissions) and partner keys never on `/api/mes`.

* `GET /intake?site=PT-CHV&limit=100` [mes:intake]: `{cases: [...]}` of `standard` cases with status `ready` routed to that site (all sites when omitted), oldest first, max 200. Item: `ref, partner {code, name}, partner_case_id, kind, parent_ref, priority, site, ready_at, expected_ship_date, spec_version (null until phase 4), brand, notes (decrypted instructions), acknowledged_warnings (the case's warnings when the partner confirmed them, else []), aligner_counts {upper, lower, templates}, items ([] until phase 4), files [{id, name, kind, arch, step, template, bytes, sha256, download_url}], bags [{aligner, arch, step, lines, barcode}], bag_personal_data`. Patient names are NEVER included. File `name` is the canonical name (`upper/U01.stl`, `lower/L12_T.pts`, `other/document.pdf`), never the partner's own file name (it may hold a patient name). `sha256` is the value stored when the file was processed. `notes` is the partner's free text and is passed on as written. Each call writes `mes.intake_read` (actor service) to every partner whose case is listed.
* `GET /files/:id` [mes:files]: decrypted stream, `Content-Disposition: attachment` with the canonical file name, audited as `file.download` (actor service, `via: mes`) to the partner org. Only files in state `ready` of `standard` cases with status ready, received or in_production that are routed to a site; anything else is `404`.
* `POST /cases/:ref/ack {mes_case_id}` [mes:intake]: `ready` to `received` (stage `received`, event `stage_reported`, `received_at`, stores `mes_case_id`). Returns `{ok, already, status}`. Repeating it with the same number is harmless (`already: true`); a different number is `409 mes_case_id_mismatch`; a number used by another case `409 mes_case_id_taken`; a case that is not ready `409 case_not_ready`; unknown reference `404`. The number is 1 to 64 characters of letters, digits and `_ . : / # -`.
* `POST /events {events:[...]}` [mes:events]: each `{event_id, case_ref | mes_case_id | (partner_code + partner_case_id), stage_code, occurred_at (ISO 8601), carrier?, tracking_number?, aligners_shipped?, hold_reason?}`, at most 500 per call (`400 too_many_events`). Response `{results: [{event_id, outcome: "applied"|"duplicate"|"ignored"|"error", message?}]}` in the order sent. Events are processed one by one in the order sent, each in its own transaction, so one bad event never blocks the rest. Idempotent on `event_id` (`mes_events.external_id`): an event that was applied or ignored before comes back as `duplicate` and is logged as a separate `duplicate` row. Errors (invalid event, unknown stage code, unknown case, shipping details missing, case not with the factory, factory number clash) do NOT reserve the `event_id`, so the sender can correct the cause and send the same event again. Unknown stage codes are errors and logged. Stage codes are matched case insensitively against the stage map; `ignore` targets come back `ignored`. Messages never repeat identifiers from the request.
* `GET /stage-map` [mes:events]: `{stage_map: [{code, target, note}]}`. Default map (seeded by migration 003 and by the demo seed, editable): `RECEIVED`, `CAD` -> received; `PRINT`, `POSTPRINT` -> printing; `THERMO` -> thermoforming; `TRIM`, `LASER` -> trimming; `POLISH`, `CLEAN` -> finishing; `QC` -> quality_check; `PACK` -> packing; `SHIP` -> shipped; `DELIVERED` -> delivered; `HOLD` -> hold; `CANCEL` -> cancelled.

## Bags (shared/bag.ts)

Bag layout lives in the org (`organizations.settings.bag`; becomes part of the signed spec in phase 4). Default: 76 x 127 mm, margin 4 mm, one bag per aligner, wear days 14, lines `{brand}`, `{case_id}`, `{aligner} {arch}`, `Step {step} of {total_steps}`, `Wear for {wear_days} days`, barcode `{ref} {aligner}`. Tokens: `{brand} {case_id} {ref} {aligner} {arch} {arch_short} {step} {step_padded} {total_steps} {wear_days} {patient_initials} {patient_name}` (`aligner` is `U01`/`L12`, `arch` is Upper/Lower, `total_steps` counts the aligners of that arch). `renderBags(layout, {ref, caseId, brand, aligners: [{arch, step}], patientName?})` returns `{aligner, arch, step, lines[], barcode}` per bag, upper first, templates never (the caller leaves them out). `{patient_name}` and `{patient_initials}` are only filled when the layout enables them (`showPatientName`, `showPatientInitials`, default off) AND the caller passes `patientName`; otherwise they are empty. `printsPersonalData(layout)` is true when a switch is on and a line or the barcode uses that token. The MES intake never passes a patient name, so its bags have those tokens empty even when the layout prints personal data (`bag_personal_data: true` tells the factory system). The bag CSV for K Line staff does pass it, audited. The Code 128 encoding itself is done by the printer system; only the barcode text is delivered.

## Retention job (worker, daily, `retention` job kind + CLI `retention`)

`services/retention.ts`. Per the brief section 19 for what exists now:

* Case files and patient names at `purge_after` (shipping + partner retention months; for direct cases: the time of a successful portal push + retention months). Cancelled cases 30 days after cancel (`purge_after` is also set to cancel + 30 days). Purging a case deletes all stored chunks, marks files `purged`, nulls the file name, wrapped key, nonce and key id (so leftover bytes could never be read), nulls the encrypted patient name, first, last, blind indexes and notes, sets `purged_at`, adds event `purged` and audit `case.purged` (actor system). The non identifying production record stays (reference, partner case ID, status, stage, dates, aligner counts, carrier and tracking, file measurements). Objects that could not be deleted are retried on the next run.
* Drafts 30 days after the last change are deleted with their files (`case.deleted`, reason retention). Abandoned uploads (files in `uploading` with no activity for 2 days) are deleted.
* Sessions 7 days after expiry or revocation; user tokens 30 days after expiry; OIDC flows 1 day; notifications 180 days; MES events 180 days; dev mailbox 14 days; finished jobs 14 days; `webhook_deliveries` 90 days when that table exists. The audit log is never touched here.
* Schedule: `startWorker` claims a daily slot (`job_runs` row `retention`, a conditional update, safe with several workers) at start and then hourly, and queues one `retention` job when the last run is older than 24 hours. `npm run ... cli retention` runs it on demand and prints counts.

## Deviations from the first draft of this contract

1. CSV import takes JSON `{csv}` or `text/csv`, not multipart.
2. Sites use camelCase in responses (`inEea`, `hasAdequacy`); bodies accept both spellings.
3. New case event type `routed` (and `rerouted` for a site change while ready).
4. Extra step up: all staff writes (including disable and enable), agreement records (POST as well as DELETE), and saving a bag layout that prints personal data. Not required: activate, suspend, settings, sites, stage map.
5. Agreements are withdrawn (soft delete), not erased.
6. The MES feed uses canonical file names and never passes a patient name to bag rendering.
7. Event log: duplicates are stored as their own rows, errors do not reserve the event ID.
8. `mes.stage_map` GET/PUT wrap the list as `{items}`; the factory API uses `{stage_map}`.
9. Release clears the site and dates, so the case returns to the review tab.
10. K Line name searches, case views, bag CSVs and factory reads are audited to the partner.

## Four step progress bar and portal status sync (supersedes the ten step stepper)

The partner sees only four statuses: Draft, Submitted, Production, Shipped (standard and direct manufacturing cases alike).

Case JSON: `simpleStatus` is `draft|submitted|production|shipped|cancelled`. `stepper` is always the four steps in that order, each `{id, label, state, detail?}`. Steps before the current one are `done`. `detail` is a short caption on the current step only: the factory stage ("3D printing") in Production, "On hold" or "Files checked" or the portal's own wording ("In planning") in Submitted, "Delivered" in Shipped. A cancelled case has all four steps `upcoming` (no current step) and `simpleStatus: "cancelled"`. The detailed factory stages are not steps any more.

Mapping (`shared/stages.ts`): `draft` is Draft; `submitted`, `on_hold`, `ready` are Submitted; `received`, `in_production` are Production; `shipped`, `delivered` are Shipped; `cancelled` is Cancelled. `portalStatusToHub(code)`: `New` Draft; `InPlanning`, `PendingPlanReview`, `PlanRejected` Submitted; `InProduction` Production; `Shipped` Shipped; anything else `null`.

`GET /api/cases` and `GET /api/console/cases` also accept `status=simple_submitted|simple_production|simple_shipped` (submitted, on_hold, ready / received, in_production / shipped, delivered). The older groups still work.

`portal` in the case JSON (direct cases) gained `demo` (true when the in memory fake was used, so nothing was sent to the K Line portal), and once the sync has read the portal `portalStatus` (raw code), `portalStatusLabel`, `syncedAt` and, after a failed check, `syncError` (fixed text).

**No credentials.** Without portal credentials the push fails with "The K Line portal is not set up for this company. Add the address, key and user ID in the portal settings." The in memory fake is used only when `PORTAL_FAKE=true` (development and tests; refused in production). Such a case shows `portal.demo: true` and the web says "Demo only, nothing was sent to the K Line portal". Demo cases are never synced.

**Job `portal.sync`** (`services/portalSync.ts`). Scheduled by the worker every 10 minutes (claim in `job_runs`, never while one is queued or running), also `cli portal-sync`. For direct cases with `portal_case_uuid`, `portal_push.status = 'pushed'`, not demo, and Hub status not shipped, delivered or cancelled (a shipped case without a tracking number is watched for 7 more days), it reads the portal case with one client per organisation, at most 200 cases per run (least recently checked first). Effects: `InProduction` sets `in_production` (stage null, `started_at` if empty); `Shipped` sets `shipped` (`shipped_at`, and `carrier` and `tracking` from `tracking_number`, which is either the number alone or "courier number"); `expected_shipping_date` sets `due_date`. Earlier portal statuses leave the case Submitted, and the Hub status only moves forward. A `stage` case event with `data.source = 'portal'` (`sourceLabel` "K Line portal", `data.message` "Status from the K Line portal: In production") is added only when the portal status changes. Moving to Production or Shipped also notifies the partner's active users (`case_stage`, `case_shipped`) and calls `emitCaseWebhook` (`case.stage_changed`, `case.shipped`). A failing case records a fixed `portal_push.syncError` and the run carries on. Each case is applied in its own transaction under a row lock, so repeats and parallel runs add nothing. No patient data appears in events, jobs, notifications or errors.

`POST /api/cases/:id/portal/refresh` (`case.read`, partners for their own organisation, K Line staff any case, API keys with `cases:read`; 30 per minute) runs the same sync for that one case and returns `{case}`. `404` for another organisation's case, `409 not_direct`, `409 not_pushed`. A demo case is returned unchanged.
