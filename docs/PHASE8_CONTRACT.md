# Contract: Case address and mandatory company logo

Owner requests (5 Oct 2026):
1. Every customer has a **Case address** (the shipping address the K Line portal keeps on each case). It is collected at registration, can be edited in the company profile afterwards, and is sent from the Hub to the staging portal with every direct manufacturing case.
2. The customer **company logo is mandatory**, with clear logo instructions (format and size). Every partner user must see their own logo after signing in: shown in the top bar of the web app, directly left of the company name.

Read first: docs/KLINE-API-2.6.txt (Add Case Shipping Address), docs/PHASE5_CONTRACT.md (registration, profile), server/src/services/{signup,profile,bulkPush,bulk}.ts, services/portal/{client,v2,fake}.ts, routes/{signup,profile,orgPortal}.ts, validate/image checks, web pages auth/Register.tsx, partner/Company.tsx, partner/Overview.tsx, layout/Shell.tsx. Additive migration only (`009_*.sql`) if needed. Interface text: plain British English, no dash separators.

## 1. Case address

Portal rule (API v2.6): `PATCH /api/v2/cases/{uuid}/shipping-address` with ALL nine fields required: `shipping_street_address` (max 255), `shipping_city` (255), `shipping_country` (ISO 3166-1 alpha-2, 2 chars), `shipping_postal_code` (max 10), `shipping_state_province` (max 64), `shipping_full_name` (255, recipient), `shipping_phone_number` (max 15), `shipping_email_address` (255), `shipping_company` (150). The portal refuses changes to the address of a submitted direct manufacturing case (409), so the Hub sets it right after creating the portal case and BEFORE submitting.

Hub data: `organizations.settings.case_address` = `{ company, fullName, street, city, postalCode, stateProvince, country, phone, email }` (camelCase in the Hub; mapped to the portal names when pushing). Limits above apply (postal code 10, phone 15, state 64); phone: digits, spaces, `+`, `-`, `(`, `)`, at most 15 characters after removing spaces? NO: the portal limit is 15 characters of the value sent, so validate the value as typed to at most 15 characters and send it as typed. `stateProvince`: required by the portal; when a country has no states the user may write `N/A` (say so in the form hint). Country uses the ISO list from `shared/signup.ts`.

Server:
* Shared validator `shared/caseAddress.ts` (`validateCaseAddress`, `CaseAddress` type, field limits, `isCompleteCaseAddress`) used by server and web (relative import / `@shared` alias).
* Registration: `POST /api/auth/register` accepts a `caseAddress` object `{street, city, postalCode, stateProvince, country, phone}` (all required when signup is on; recipient name, company and email default to the registrant's person name, company name and email; the registrant can change them later). Invalid input answers 400 with field messages as today. Stored in `settings.case_address` when the organisation is created. The "always the same answer, never faster than 600 ms" rules are unchanged. Update the Contoso and Fabrikam seed orgs and Acme with fictional complete addresses.
* Profile: `GET /api/org/profile` returns `caseAddress` (object or null) and `caseAddressComplete: boolean`; `PUT /api/org/profile` accepts `caseAddress` (partial update allowed, merged, validated as a whole when complete; org.edit; audited). Add the case address to `GET /api/org/onboarding` checklist as item `case_address` (done when complete).
* Push: add `setShippingAddress(caseUuid, address)` to the `PortalClient` interface, the v2 client (PATCH, JSON body with the nine portal fields, same error mapping and timeouts, no patient data) and the fake client (store it so tests can assert). In `bulkPush`, after the portal case is created (or if the case exists but `portal_push.uploads.address` is not true) call it once and record `uploads.address = true` so a retry does not repeat it; then upload files and submit. If the organisation's case address is missing or incomplete, the push fails permanently with the fixed message "Add your case address in the company profile, then press Try again." (no retries). Changing the profile address later does not change cases already pushed (the portal forbids it).
* Early gate: `POST /api/bulk/batches` and submit of a direct case answer `409 case_address_required` with that message when the address is incomplete, so the partner learns before uploading 1 GB of files.
* Case JSON for direct cases includes `shippingAddress` is NOT needed; do not expose the address on case lists. Webhooks and exports do not include it.
* Tests: validator unit tests (limits, country codes, phone), registration with and without address, profile read/write permissions, onboarding checklist item, push order (createCase, setShippingAddress, uploads, submit) with the fake client, address sent exactly as mapped, idempotent retry, fixed failure message without address, early 409 gate, other orgs isolated, existing tests adjusted deliberately.

## 2. Mandatory company logo

Rules (document them in the UI and in docs/PARTNER_GUIDE.md):
* Formats: PNG (best, transparent background), SVG (safe subset, checked by the existing SVG validator) or JPG. Maximum file size 2 MB (change the logo limit from 5 MB to 2 MB for the company logo only if the code allows per kind limits; otherwise keep 5 MB and say "up to 2 MB recommended" and enforce 2 MB in the new company logo route).
* Size: PNG/JPG at least 400 x 120 pixels and at most 4000 x 4000; recommended 800 x 240 pixels (landscape, ratio about 3 to 1) for a sharp display on high resolution screens; width to height ratio between 1:1 and 6:1 (wider than tall, or square). SVG needs a `viewBox` (or width and height) whose ratio is in the same range. Keep about 10 percent empty margin around the artwork; use a transparent background; dark artwork must still be readable on a white top bar.
* Server validation on `POST /api/org/logo` (and keep brand logos as before): read PNG and JPEG dimensions from the file header after decryption at attach time, SVG from `viewBox`/`width`/`height`; refuse with a friendly 422 `logo_too_small|logo_too_large|logo_bad_ratio|logo_type` message that repeats the instruction. The upload stays encrypted like any file.
* Mandatory: `GET /api/org/profile` returns `logoRequired: true`, `hasLogo`; `GET /api/org/onboarding` adds item `logo`; `POST /api/partners/:id/activate` adds blocker `logo_required` (K Line cannot approve a company without a logo) and the partner detail `gates.blockers` lists it; the console partner page shows it. Active companies without a logo (older data) are not blocked from working but see a banner everywhere until they add one. Seed: Acme, Contoso and Fabrikam get a generated fictional logo (small valid PNG or SVG from `demo/assets.ts`), keeping tests green.
* Display: `GET /api/org` (the org summary used by the shell) returns `logo: {hasLogo, version}` where `version` changes when the logo changes (use the file id or `updated_at` epoch) so the browser can cache bust; `GET /api/org/logo` already streams the decrypted image with `nosniff` and a sandbox CSP: make sure it works as an `<img src>` (cookie auth, `Content-Type` set to the real image type, `Cache-Control: private, max-age=3600`, not `no-store`), SVG served with `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; sandbox` so scripts can never run.
* Tests: dimension parsing for PNG/JPEG/SVG, accepted and refused samples, size limit, tenant isolation, activation blocker, checklist item, content type and cache headers, SVG still sanitised.

K Line staff keep the K Line mark. Keep the K Line square mark in the sidebar (platform branding).

You can change it later in your company profile."), validation with the shared validator, field level server errors. Do not ask for the logo at registration (it needs a signed in session); say "You will add your logo after you sign in."
* Company profile (`pages/partner/Company.tsx`): a **Case address** card (all nine fields, recipient name, company, email prefilled from registration; save with the shared validator; read only without org.edit) and a **Logo** card marked as required with the instructions panel (formats, recommended 800 x 240 px, minimum 400 x 120, maximum 2 MB, transparent background, margin, "must be readable on white"), a live preview exactly as it will appear in the top bar (on white), browser side pre-check of file type, size and pixel dimensions with the same limits and friendly messages before uploading, replace and remove. ## Deviations (server, 5 Oct 2026)

What the server does that differs from, or adds to, the text above. Web code can rely on this section.

1. **Registration.** `validateRegistration` in `shared/signup.ts` now also validates `caseAddress` and returns it in `value.caseAddress` (a full `CaseAddress`). Field paths are `caseAddress.street`, `caseAddress.city`, `caseAddress.postalCode`, `caseAddress.stateProvince`, `caseAddress.country`, `caseAddress.phone` (and `caseAddress.company`, `.fullName`, `.email` when those are typed). The recipient name, company and email are optional in the request: when empty or missing they default to the person name, company name and email of the registrant. The server stores `settings.case_address` with all nine fields. No address, or a wrong one, answers 400 `invalid_request` with `fields: [{path, message}]` before anything is looked up.
2. **New shared file `shared/logo.ts`.** Limits (`LOGO_MAX_BYTES` 2 MB, minimum 400 x 120, maximum 4000 x 4000, ratio 1 to 6), the instruction text (`LOGO_INSTRUCTIONS`), `checkLogoBytes`, `checkLogoDimensions(format, width, height)` and header readers (`pngSize`, `jpegSize`, `svgSize`, `checkLogoFile`). The web pre-check can import it so both sides give the same messages. `shared/caseAddress.ts` exports `validateCaseAddress`, `validateCaseAddressPatch`, `validateCaseAddressField`, `isCompleteCaseAddress`, `caseAddressView`, `CASE_ADDRESS_LIMITS`, `CASE_ADDRESS_LABELS`, `STATE_PROVINCE_HINT` and `CASE_ADDRESS_REQUIRED_MESSAGE`. Field rules: every field required; postal code letters, digits, spaces and dashes (at most 10); phone digits, spaces and `+ - ( )` with at least 5 digits and at most 15 characters as typed; state or province at most 64 (`N/A` is accepted); country must be in the ISO list (stored upper case); no `<`, `>` or control characters.
3. **Profile.** `GET /api/org/profile` adds `caseAddress` (object with all nine keys, empty strings for parts that are missing, or `null` when nothing is stored), `caseAddressComplete`, `logoRequired: true` and a top level `hasLogo`. `logo` stays and becomes `{hasLogo, version}`. `PUT /api/org/profile` accepts a partial `caseAddress`: every field given is validated with the shared rules (an empty string is an error, there is no way to clear a field), the result is merged into the stored address and the address can be incomplete until every field is set. Errors are 400 `invalid_request` with `fields` paths like `caseAddress.phone`. Audited as `org.profile_updated` with `changed: ['caseAddress']` and no values.
4. **Checklist.** `GET /api/org/onboarding` items are now, in this order: `account_secured`, `profile`, `logo` ("Add your company logo"), `case_address` ("Add your case address"), `spec`, `dpa`, `approval`.
5. **Logo upload and attach.** `POST /api/uploads` still accepts up to 5 MB for a logo (the upload route cannot tell a company logo from a brand logo). `POST /api/org/logo` enforces the rules at attach time and answers 422 with `code` `logo_too_small`, `logo_too_large` (file over 2 MB, or more than 4000 pixels), `logo_bad_ratio` (also an SVG without a usable viewBox or width and height) or `logo_type` (the size cannot be read). The `message` repeats the instruction. A refused file is deleted at once, so it does not use one of the 10 profile file slots of an unapproved company. Brand logos are checked as before, without the new size rules. `POST /api/org/logo` now answers `{hasLogo: true, version}`.
6. **`GET /api/org`** adds `logo: {hasLogo, version}`. `version` is the id of the stored logo file (it changes whenever the logo changes) and `null` without a logo. Use `/api/org/logo?v=<version>` as the image address. K Line staff get `{hasLogo: false, version: null}`.
7. **Logo response headers** (company logo, brand logos and the console route `GET /api/partners/:id/logo`): `Content-Type` is the stored image type, `Cache-Control: private, max-age=3600`, `X-Content-Type-Options: nosniff`, `Content-Disposition: inline`, and for every image type (not only SVG) `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; sandbox`. The global `no-store` rule for `/api` no longer overwrites a cache header a route set itself, but error answers (status 400 and up) are always `no-store`.
8. **Activation.** `POST /api/partners/:id/activate` answers 409 `logo_required` ("The company needs a logo before it can be approved. Ask the company to add it in its profile."). It is checked after the other conditions. `GET /api/partners/:id` adds `gates.hasLogo`, top level `caseAddress` and `caseAddressComplete`, and `gates.blockers` lists `{code: 'logo_required', message: 'Company logo is required.'}` after the other blockers; `canActivate` is false without a logo. Companies that are already active are not blocked.
9. **Gates for the case address.** `POST /api/bulk/batches` and `POST /api/cases/:id/submit` (direct manufacturing cases only) answer `409 {code: 'case_address_required', message: 'Add your case address in the company profile, then press Try again.'}` when the address is missing or incomplete. The batch route checks before creating anything. The same message is the portal push failure text (`portal.lastError`), the push stops without retries, and the `portal_push_failed` event carries `code: 'case_address_required'`. Standard cases and other organisations are not affected. An address counts as complete only when all nine fields pass the shared validator.
10. **Push order** is: create the case, set the shipping address (once, recorded as `portal_push.uploads.address = true`), upload files, submit. A case that already has a portal case without `uploads.address` gets the address on its next push. A retry after a failure never creates a second case and never repeats the address.
11. **Fake portal client.** `setShippingAddress` stores the nine portal fields on the fake case (`shippingAddress`), refuses an incomplete address with a validation error (400) and refuses a submitted case (409), like the real portal. `FakeOp` gains `'setShippingAddress'`. `toPortalShipping(address)` in `services/portal/client.ts` is the single mapping from Hub names to portal names.
12. **No migration.** The address lives in `organizations.settings.case_address` and the push progress in `cases.portal_push`, so migration `009` was not needed. Rewrap is unaffected (the address holds company details, not patient data, and is not encrypted).
13. **Seed.** Acme, Contoso and Fabrikam have fictional complete case addresses and a generated SVG logo (`sampleLogoSvg` in `demo/assets.ts`), stored encrypted like an upload. The seed was NOT run against the shared development database. Run `npm run seed` there only when the owner agrees (it wipes the data).
14. **Open point for the owner.** The portal documentation lists `shipping_state_province` as required but does not say whether `N/A` is accepted. The Hub sends whatever the partner typed. Tested on 5 Oct 2026 against the staging portal: all nine fields are accepted and read back unchanged, and `N/A` is accepted for the state or province.

## Deviations: case address per user (5 Oct 2026)

Owner request: "Make each user able to change his own Case Address." The company address above stays as the **default**; every partner user can add an address of their own.

15. **Migration `010_user_case_address.sql`** adds `users.case_address jsonb` (nullable, additive). Row level security on `users` is unchanged. Null means "none, use the company address". The value holds the same nine fields as the company address.
16. **Routes (any signed in partner user, any role, no permission needed beyond the full session).** `GET /api/account/case-address` answers `{own, ownComplete, company, companyComplete, effective}` where `own` and `company` are the nine field object (empty strings for missing parts) or `null`, and `effective` is `'own'`, `'company'` or `'none'`. `PUT /api/account/case-address` replaces the caller's own address: all nine fields are required and checked with `validateCaseAddress` (400 `invalid_request` with `fields` paths such as `street`, no `caseAddress.` prefix; unknown keys are ignored). `DELETE /api/account/case-address` removes it. PUT and DELETE answer the same shape as GET. There is no user id in any route or body: a person can only ever read or change their own address. K Line staff and partner API keys get 403, visitors 401. Audited as `account.case_address_changed` with `{changed: [field names], removed: boolean}` and never any value.
17. **Which address a direct case is sent with.** The address of the person who **created** the case (`cases.created_by`, set when the batch or case is created) when that user belongs to the case's company and has a complete own address, otherwise the company address, otherwise nothing. The person who presses submit and the worker that pushes do not matter. The rule is `resolveCaseAddress` and `pickCaseAddress` in `services/userCaseAddress.ts`. Cases created through the partner API with a key have no creator (`created_by` is null), so they always use the company address (a key is not a person). A creator who has since been disabled still counts (users are never deleted). An incomplete own address (not possible through the route, only through old or manual data) counts as none, so the company address is used.
18. **When it is resolved.** The push reads the creator's own address and the company address when it starts and uses them at the address step, so a person who saves an address after creating a case but before the push runs gets it used. Once `portal_push.uploads.address` is true nothing is sent again, so a later change never touches a case that was already sent (the portal would refuse it anyway). The push now records `portal_push.addressSource` (`'own'` or `'company'`, never values) next to `uploads.address`. It is not part of the case JSON, lists, webhooks, exports or the partner API. Cases pushed before this change have no `addressSource`.
19. **Early gates.** `POST /api/bulk/batches` checks the effective address of the caller (own, else company; a key uses the company one). `POST /api/cases/:id/submit` for a direct case checks the effective address of the case's creator. Both answer `409 case_address_required` before anything is created or uploaded when neither is complete. The message is unchanged ("Add your case address in the company profile, then press Try again.") and it is also the permanent push failure text.
20. **Onboarding and approval stay on the company address.** The `case_address` checklist item of `GET /api/org/onboarding`, the profile `caseAddressComplete`, and the console partner page are unchanged and look at the company address only. The web checklist on the overview shows the item as done when the person's effective address is not `none`, and links to Account for people who cannot edit the company profile. `GET /api/account/case-address` is where the web app reads `effective`.
21. **Web.** The Account page has a **Case address** card for every partner user (anchor `#case-address`): which address is in use, the company address read only (with a link to the company profile for administrators), and a form with the nine fields that starts from the company address as a template (recipient name and email default to the person's name and email). Buttons: **Save my case address** and **Use the company address instead** (confirmation, DELETE). The company profile card is now called **Company case address** and says it is the default. The Direct manufacturing notice uses `effective === 'none'`. The friendly message for `case_address_required` now says "in your account or in the company profile".
22. **Partner API.** Keys have no user: direct cases created through `/api/v1` are sent with the company address (see docs/integration/PARTNER_API.md).
23. **Tests.** `server/test/phase8.useraddress.test.ts` (routes, permissions, tenant isolation, validation, audit, push source, early gates, retries). `phase8.test.ts` only gained an `addressSource` assertion.
