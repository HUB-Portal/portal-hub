Authentication

To access the API endpoints you need an API secret key coupled with your UUID. You send those in your
request headers for each request as X-KLINE-API-KEY and X-KLINE-API-USER-UUID . Your user UUID is
the trailing string in the URL when you visit My Account screen.
Generate API Secret Key

Navigate to your account on the portal. Find the "Generate API Key" button under your account. If you
can't find it, your account does not have the necessary permissions to generate an API Secret key. Contact
your portal administrator to request the permission.

Click the "Generate API Key" button. You need to accept K Line API terms of service then proceed. A new
API Secret key will be generated and displayed only once. Copy the key and keep it safe. Do not share it
with anyone.

Generate a new API Secret Key

If your account already has an API Secret key, you can generate a new one by clicking the "Generate API
Key" button again. You will be prompted that the old key will be invalidated before creating a new one. If
you agree, the new key will be generated and displayed only once. The old key will no longer be valid.
Make sure to replace the old key with the new one in your application(s).

Endpoints

Base path for all endpoints is /api/v2/ . Endpoints can have parameters as part of the path. The
parameters are shown in the path of each endpoint with curly braces. For example, {case_uuid} .

Endpoints can have options sent as query string parameters. These are defined in each endpoint section
below as query string parameters.

POST and PATCH requests should have body content. The body is sent as JSON. The keys and expected
values are shown under the body section of each endpoint.

Each request should have a content-type header. The value of this header is shown under the headers
section of each endpoint.

Additional headers are shown under the headers section of each endpoint.

Response Template

HTTP response code should be checked. Errors will be communicated through response codes. Anything
other than 200 , 301 , or 302 will include an error message in the response JSON. The standard
response format is as follows, see each endpoint details for more information about that specific endpoint
response.

{
   "message": "A message in case of error responses",
   "data": [ // an array in case of multiple items response, otherwise a single item
       {
          "key": "value" // an item represented in key:value pairs
       }
   ],
   "metadata": "value" // if the response provides metadata, each metadata item will be provid

}

Update Case

Updates an existing case that is still in draft state. Only specific fields are allowed to be updated. If the
case is no longer in draft (field_case_status  New), the update will be rejected.
path: cases/{uuid}
method: PATCH
headers:

Content-Type: application/json

X-Kline-Doctor-Id: Optional. The ID of the doctor that owns the case. It will replace the current case doctor.
query string parameters:
none
body:
One or more fields from the Add Case body fields, except the product_type which cannot be changed
after case creation. The new values of the fields overrides the old values. All other fields will not be
changed.

fields are inherited from the parent case; only the fields listed below can be supplied in the request body.

 product_type is always set to 4 (Whitening Tray).

path: cases/{case_uuid}/whitening-tray

method: POST

headers:

content-type: application/json

caller's hierarchy. Defaults to the parent case's doctor.

query string parameters: none
body: All fields optional.

impression_type      Integer  Which arches to treat. See arches treatment.   No
treat

Datetime Values

Datetime values are represented as ISO 8601 strings. For example, the following are valid datetime values:

        2020-01-01T00:00:00+01:00
        2020-01-01T00:00:00.000Z

To avoid ambiguity, when sending datetime values, always include the timezone offset. If the offset is not
specified, it is assumed to be Z (UTC).

Webhooks

Webhooks are used to notify your application when an event occurs in the K Line system. For example
when a case is added or updated, or when a new doctor signed up. All webhook requests are POST
requests. The body of the request is a JSON object with the event payload. Check Webhook Payload for
the payload structure. The headers of the request are:

        Content-Type: application/json

       X-KLINE-SECRET-TOKEN : The optional secret token configured in the webhook.

Managing Webhooks

In the portal UI, click your avatar to show the user menu, click API Webhooks. This opens a dashboard
where you can manage your webhooks.

Create a Webhook

Click the "Add Webhook" button. This opens a form where you can configure the webhook. The form has
the following fields:

Label: A label for the webhook. This is used to identify the webhook in the dashboard.

URL: The URL where the webhook will be sent. This is the URL of your application. The URL must be
accessible from the K Line system. The URL must be a valid https URL.

Triggers: The triggers that will cause the webhook to be sent. You need to select at least one trigger.

Enabled: Whether the webhook is enabled or not. If the webhook is disabled, it will not be triggered by its
events. You can only have up to 5 enabled webhooks at the same time.

Secret Token: An optional secret token that will be sent with the webhook. This is used to authenticate the
webhook in your application. Even though it's optional, we strongly recommend that you make use of it for
the added security it provides. The secret token must be a string of at least 16 characters. It is
recommended to use a random string of characters. This token will be sent in the X-KLINE-SECRET-TOKEN
header in the webhook request.

Edit a Webhook

In the dashboard listing your webhooks, there is a dropdown button next to each webhook. The default
action is to edit the webhook. Click the button to open the form to edit the webhook.
Delete a Webhook

In the dashboard listing your webhooks, there is a dropdown button next to each webhook. Expand the
dropdown and click the "Delete" button. This will delete the webhook.

Testing Webhooks

You can test your webhooks by sending a test request. In the dashboard listing your webhooks, there is a
dropdown button next to each webhook. Expand the dropdown and click the "Test" button. This will send a
test request to your webhook. The test request will be sent to the URL you configured in the webhook. The
test results will be displayed in the dashboard with details of any errors if any.
